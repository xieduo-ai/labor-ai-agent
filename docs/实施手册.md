## 4. 第二周：切分与索引

### 4.1 为什么按"条"切，不按字数切

通用 RAG 教程都教你按 500 字切、重叠 50 字。**在法律文本上这是错的**：法条是原子语义单元，"试用期不得超过六个月"和它的例外（"以完成一定工作任务为期限的劳动合同不得约定试用期"）如果被劈到两个 chunk，模型只会看到前半句，然后自信地答错。

所以：**一条 = 一个 chunk**，元数据带法律名、章、条号。检索时可以用法律名过滤，生成时可以精确引用到"第X条"。

### 4.2 跑起来

```bash
python -m src.ingest
```

预期输出：

```
共 16 个文件，1842 条
  中华人民共和国劳动合同法                          98 条
  中华人民共和国劳动法                             107 条
  ...
已写入 ...\data\processed\chunks.jsonl
```

**逐项检查**：

1. 每个法的条数对不对（对第 3.4 节的锚点）。
2. 有没有 `[警告] xxx 解析出 0 条` —— 说明格式不对（多半是"第X条"没顶格，或者编码乱了）。
3. 有没有 `[警告] 重复条文` —— 说明文件里粘重了。

### 4.3 抽查 30 条（这步别偷懒）

打开 `data/processed/chunks.jsonl`，随机翻：

- 每条 `text` 是不是完整一句话？有没有被截断？
- `chapter` 对不对？有没有一条本该在"第四章"却标成"第三章"（说明章标题行没识别到）？
- `article_no` 和正文里的条号一致吗？

**常见的三个 bug 和修法**：

| 现象 | 原因 | 修法 |
|---|---|---|
| 某章之后条数突然变少 | 章标题写成 `第一章 总则`（半角空格）以外的形式，或中间夹了"（一）" | 看 `CHAP_RE`，把实际格式加进去 |
| 一条被拆成两条 | 正文里有 `第三条` 出现在行首（比如引用其他法） | 检查该行，手工加个全角空格缩进，或在该行前加 `>` 标记后过滤 |
| 条号跳号 | 有的法有 `第九十八条之一` | 属于少数，先忽略，记到 README 的局限里 |

### 4.4 建索引

```bash
python -m src.index
```

做三件事：调 `bge-m3` 把每条变成 1024 维向量（首次 2–5 分钟，按条计费很便宜）→ 归一化存成 `embeddings.npy` → jieba 分词建 BM25 存 `bm25.pkl`。

**注意 embedding 的输入文本**（`index.py` 里的 `embed_text`）：

```python
f"《{c['law_name']}》{c['chapter']} {c['article_no']} {c['text']}"
```

为什么要加法律名和条号？因为"第三十九条"这四个字本身毫无语义，但结合"《劳动合同法》第四章 第三十九条"就能区分"过失性辞退"和"劳动争议时效"。**这是个小设计，但面试时能讲成一个细节。**


## 5. 第三周：检索与问答

### 5.1 先搞懂 RRF 在干什么

两周召回各给 20 条，怎么合并？最简单的是"分数相加"，但 BM25 分数是 0–20 的无界值，余弦相似度是 0–1，量纲不同，没法加。

**RRF（Reciprocal Rank Fusion）只用排名，不用分数**：

```
score(d) = Σ  1 / (60 + rank_i(d))
```

一个文档在两路里都排第 3，得分就是 `1/63 + 1/63`；只在一路排第 1，是 `1/61`。**两路都认可 > 单路极强**，这正是我们要的。k=60 是原论文的经验值，不用调。

代码在 `src/retrieve.py`，一共 8 行，建议你手敲一遍，比复制粘贴记得牢。

### 5.2 再搞懂重排

向量检索是"双塔"：query 和 doc 分别编码再算相似度，快但粗。
Cross-Encoder 把 query 和 doc **拼在一起**过一次模型，慢但准。

所以流程是：**粗排召回 20 条 → 精排取前 6 条**。这就是工业界标准的"召回-排序"两阶段。面试问"你的 RAG 怎么做的"，答出这四个字就比大部分人强。

### 5.3 问答 prompt 的三个关键约束

看 `src/prompts.py` 里的 `QA_SYSTEM`，三条规则是核心：

1. **只能依据参考资料** —— 防幻觉的第一道闸。
2. **每条结论必须标注【《法律》第X条】** —— 让用户能自己核，也让错误可追溯。
3. **资料不足就说不足** —— 这条最容易被忽略。不设这条，模型遇到知识库没有的问题（比如"深圳的育儿假多少天"）会编一个数字，而且是那种看起来很合理的数字。**能拒答的 RAG 才是能用的 RAG。**

### 5.4 迭代方法（重要）

不要一次写 20 个问题测。**一次只测 1 个问题，改一处 prompt，再测。**

准备一个 `notes.md`，格式：

```
## Q: 公司没提前30天通知就辞退，要赔多少？
- v1 回答：只说了 N+1，没提违法解除是 2N  ← 问题：没区分合法/违法
- 改法：prompt 加"先判断解除是否合法，再算补偿"
- v2 回答：ok，但没引用第87条
- 改法：参考资料里补入第87条（检索没召回，是检索问题不是 prompt 问题）
```

**这个 notes 就是面试时最好的素材**，因为它证明你真的在调试而不是拼装。

### 5.5 本周验收

20 个问题，覆盖：试用期、加班费、解除、经济补偿、工伤、竞业、女工、社保。

- ≥18 题没有编造法条

## 6. 第四周：合同审查（项目的差异点）

> 前三周的东西，网上教程一大把。**这一周才是别人抄不走的**——因为只有懂劳动关系的人知道该查什么。

### 6.1 先准备测试合同

两条路，都要走：

**（a）真实示范文本**：人社部官网有《劳动合同（通用）》示范文本，湖北人社厅也有本地版。下 1–2 份当"正常样本"，用来测**误报率**（正常合同不该报一堆高风险）。

**（b）自己写"有坑版"**：这是你的专业优势。手写 3 份，每份埋 4–6 个坑，作为"标准答案"。必须埋的坑：

| 埋的坑 | 违反 | 依据 |
|---|---|---|
| 合同期 1 年，试用期 6 个月 | 试用期上限 | 劳动合同法第 19 条 |
| 试用期工资为转正工资的 60% 且低于当地最低工资 | 试用期工资下限 | 第 20 条 |
| "员工自愿放弃缴纳社会保险" | 社保强制 | 社会保险法 |
| 竞业限制 2 年，未约定经济补偿 | 竞业限制补偿 | 第 23、24 条 |
| "提前离职须支付违约金 5 万元" | 违约金法定情形 | 第 25 条（只有培训服务期、竞业限制两种） |
| "公司有权根据经营需要单方调整岗位和薪资" | 变更需协商一致 | 第 35 条 |
| "加班费已包含在月薪中，不再另行支付" | 加班费 | 劳动法第 44 条 |
| "女职工入职三年内不得生育" | 就业性别歧视 | 妇女权益保障法 |

写的时候故意用真实合同的语气（"甲乙双方本着平等自愿……"），别写成考题。这样才测得出模型在噪声里的表现。

### 6.2 三个模块

**（1）条款切分**（`split_clauses`）

用正则匹配 `第X条` / `一、` / `1.` / `（一）`。**先跑通，别追求完美**。第一版一定会把"第一条"和它下面的"（一）（二）"切开，这没关系，反而让审查更细。

**（2）逐条审查**（`review_clause`）

每条：检索 top-4 法条 → 拼进 prompt → 要求输出严格 JSON。

为什么要 **逐条** 而不把整份合同丢进去？两个原因：
- 合同动辄 3000 字，一次丢进去模型会"平均化"，只挑最明显的坑说；
- 逐条才能给出"哪一条有问题"的精确定位，这才是产品价值。

代价是调用次数多（25 条 = 25 次调用），但 DeepSeek 便宜，一份合同约 0.1–0.3 元，可接受。

**（3）引用有效性校验**（`_check_basis`）

这一步是**防幻觉的硬手段**：模型说"依据《劳动合同法》第八十五条"，代码去知识库里查，查不到就标 `exists: False`。

面试官问"你怎么保证不编法条"，标准答案不是"我 prompt 写得好"，而是**"我有程序化校验，编造率可以量化"**。前者的可信度是 0，后者是 100。

### 6.3 本周验收

拿 3 份自造合同跑：

- 人工埋了 10 个坑，抓到 ≥7 个（**风险召回率 70%**）
- 正常示范合同上，报出的"高风险" ≤1 条（**误报率**要低，不然产品没法用）
- 每条风险都有法条依据，且 `exists` 全为 True

把这三个数字记下来，第五周要用。

### 6.4 一个容易踩的坑

`json_mode=True` 时，DeepSeek 偶尔会返回空字符串或带 markdown 代码块围栏的 JSON。代码里已经做了 `try/except json.JSONDecodeError` 兜底，但如果失败率高（>10%），在 prompt 末尾再加一句"直接输出 JSON，不要用 ``` 包裹"。

## 7. 第五周：评测（决定这个项目是"玩具"还是"作品"）

> 90% 的学生项目死在这里：能 demo，但没有数字。有数字的项目，面试通过率不是一个量级。

### 7.1 建评测集（150 题，两天）

`eval/qa_set.jsonl`，每行：

```json
{"qid": 12, "question": "公司让我周末加班但不给加班费，合法吗？",
 "gold_articles": ["中华人民共和国劳动法#第四十四条"],
 "category": "工时加班", "difficulty": "易"}
```

**出题原则**：

1. **分层配额**，别随机出。建议：订立 20 / 试用期 15 / 薪酬工时 20 / 解除终止 30 / 经济补偿 15 / 工伤 15 / 女工与医疗期 10 / 竞业保密 10 / 社保 10 / 新业态用工 5
2. **必须是真实问法**，不要照抄法条原文。去知乎、贴吧、HR 社群里捞真实提问，或者用裁判文书里的"争议焦点"改写。
3. **绝对不能用自己的模型生成题目**——那等于自己出题自己考，评测结果毫无意义。这是评测的第一原则。
4. 先做 80 题跑通流程，再补到 150。**不要一次写 150 题，会崩溃。**

**标注 `gold_articles` 的时候，你就是专家**。这是劳动关系专业给你的、CS 同学没有的能力——他们连"这个案子该引第 39 条还是第 40 条"都分不清。

### 7.2 算指标

```bash
python eval/run_eval.py
```

输出 `Recall@5` 和按类别拆分的表。**重点看哪个 category 最低**，那就是下一步要改的地方。

（Recall@5 = 正确法条是否出现在检索结果前 5 条里。注意这是**检索指标**，不是回答质量指标。）

### 7.3 消融实验（这张表最值钱）

```bash
python eval/ablate.py
```

预期能跑出类似这样的对比：

```
① 纯向量          58.7%
② 纯 BM25         64.0%
③ 混合 RRF        78.0%
④ 混合 + 重排      84.7%
```

**这就是你简历上那一行**：*"通过 BM25+向量混合检索与 Cross-Encoder 重排，将法条检索 Recall@5 从 58.7% 提升至 84.7%"*。

如果混合反而比单路低，通常是两个原因：BM25 分词把法律术语切碎了（在 jieba 里 `jieba.add_word("经济补偿")` 加自定义词典），或者 rerank 模型对短文本不敏感（把 `top_n` 调大试试）。

### 7.4 错误分析（比指标本身重要）

打开 `eval/retrieval_result.csv`，筛出 `hit@5 = False` 的，逐条归类：

| 错误类型 | 表现 | 改法 |
|---|---|---|
| 检索没召回 | 正确条文根本不在前 20 | 加自定义词典 / 换 embedding / query 改写 |
| 召回了但没用上 | 前 5 有正确条文，但模型引了别的 | 改 prompt，要求"优先使用与问题最直接相关的条文" |
| 法条理解错 | 引对了条但解释反了 | 换更强模型 / 加 few-shot 示例 |
| 地方口径缺失 | 问湖北的具体标准，答了全国规定 | 补地方数据 |

**把这张表放进 README 或者博客**。它传达的信号是："这个人知道系统哪里不行"——这比"我的系统很准"可信十倍。

### 7.5 人工评分（抽 50 条，半天）

检索指标不等于回答质量。抽 50 条，人工打 0 / 0.5 / 1 分：

- **1 分**：结论正确，引用正确，可直接用
- **0.5 分**：结论对但引用不全，或表述含糊
- **0 分**：结论错，或编造法条

算个平均分。**这个数字（比如 0.82）比 Recall@5 更能代表产品水平**，而且要写进 README，注明"人工评估，n=50"。

## 附录 B：面试怎么讲这个项目（8 个必被问的问题）

**Q1：简单介绍一下这个项目。**
> 20 秒版本：中小企业没有法务，劳动合同里的坑常年没人查，通用大模型又会编法条。我做了个系统，上传合同能逐条给出风险等级、法条依据和修改建议，核心是一条混合检索 + 强制引用的 RAG pipeline，法条检索 Recall@5 84.7%，合同风险召回 80%。

**Q2：为什么按条切分，不按固定长度？**
> 法条是原子语义单元。按 512 字切会把"试用期不得超过六个月"和它的例外劈开，模型只看到半句就会答错。而且按条切能精确保留"第X条"这个引用锚点，这是法律场景的硬需求——用户必须能自己去核。

**Q3：为什么要混合检索？RRF 是什么？**
> 法律问题里精确术语多（代通知金、竞业限制），BM25 打得准；用户口语化提问（"公司让我走人不给钱"）只有向量能懂。两路分数不可比，所以用 RRF，只用排名不用分数，k=60，不需要调权重。消融实验显示单路 58–64%，混合到 78%，加 re-rank 到 84.7%。

**Q4：怎么防止模型编法条？**
> 三层：prompt 强制引用格式；程序化校验——模型输出的每条法条去知识库里比对，不存在就标红；资料不足时明确拒答。第三层最容易被忽略，但不设的话，问一个知识库没覆盖的地方规定，它会编一个看起来特别合理的数字。

**Q5：为什么不用向量数据库？**
> 语料只有 1800 条，numpy 矩阵算余弦相似度几毫秒，装 Chroma 的调试成本比收益高。我知道生产环境该用 Milvus，也知道 HNSW 的参数怎么调，但这个规模下暴力检索就是对的工程选择。

**Q6：你这个系统最大的问题是什么？**（一定会问）
> 地方口径覆盖不全，只有湖北和几个主要省市，其他地方会答得偏保守；合同切分靠正则，扫描件会切错；没有多轮追问，用户一次问不清就得重问。下一步优先级是把地方数据补齐，然后做 query 改写。

**Q7：如果给你一个月继续做，你做什么？**
> 先做 query 改写（把口语问题改写成法律检索式），这是现在错误分析里最大的一类；然后加多轮澄清，因为真实咨询往往是"我先说说我的情况"；最后做 LLM-as-judge 的自动化评测，现在人工评 50 条太慢。

**Q8：这跟你的专业什么关系？**
> 劳动关系是业务侧，AI 是工具侧。市面上做法律 AI 的人要么懂法不懂模型，要么懂模型不懂法——标注"这个案子该引第 39 条还是第 40 条"这件事，CS 背景的人做不了，这就是我的位置。
